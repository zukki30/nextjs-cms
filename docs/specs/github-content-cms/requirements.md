# 要件定義書: GitHub ベース ヘッドレス CMS

- spec 名: `github-content-cms`
- 作成日: 2026-10-20
- ステータス: レビュー待ち

---

## 1. 背景と目的

News / FAQ / Blog を管理する管理画面（Admin）と、その内容を配信する公開 API を構築する。

コンテンツの保存先として RDB を使わず、**GitHub リポジトリ上の Markdown ファイル**を正とする。これにより以下を得る。

- データベースの運用コスト・費用がゼロになる
- 変更履歴・差分・復元が Git の仕組みでそのまま手に入る（= 監査ログが標準装備）
- 公開前レビューを GitHub の Pull Request でそのまま行える

画像のみ Git には置かず、外部の画像配信サービスで管理する。

### 1.1 このリポジトリの現状

`main` / 作業ブランチともに README.md のみが存在する（`chore: remove all project files except README` 済み）。
過去に存在した Drizzle ORM / PostgreSQL / Better Auth によるログイン実装は**本仕様では一切引き継がない**。Next.js アプリケーションの初期化から着手する。

## 2. 用語定義

| 用語 | 定義 |
| --- | --- |
| Admin | 本リポジトリに含まれる管理画面 UI（`/admin` 配下） |
| 公開 API | 外部サイトが参照する読み取り専用 API（`/api/v1` 配下） |
| 管理 API | Admin が使用する書き込み API（`/api/admin` 配下） |
| content リポジトリ | コンテンツの `.md` を保管する別の private リポジトリ |
| コンテンツタイプ | `news` / `blog` / `faq` の3種 |
| エントリ | コンテンツタイプに属する個別の記事・項目（1ファイル = 1エントリ） |
| タクソノミー | カテゴリーおよびタグの総称 |
| 下書き | content リポジトリの main にマージされていない作業ブランチ上のエントリ |
| インデックス | 全エントリのメタデータを集約した `index.json` |

## 3. スコープ

### 3.1 対象

- Admin: News / FAQ / Blog の作成・編集・削除・下書き・公開
- Admin: News / Blog のカテゴリー・タグの作成・編集・削除
- Admin: 画像のアップロード・一覧・削除・エントリへの紐付け
- 公開 API: 3コンテンツタイプの一覧取得・詳細取得・タクソノミー一覧取得
- 管理 API: 上記 Admin 操作に対応する書き込み処理
- GitHub OAuth による Admin へのアクセス制御

### 3.2 対象外（本仕様では作らない）

- 公開サイト（記事を表示する Web サイト本体）。**別リポジトリ・別デプロイ**とし、本仕様では公開 API を提供するところまでを担う。利用側への推奨実装は design.md 9.7 に記載する
- 公開サイト側のプレビュー実装（Draft Mode の有効化・データ取得先の切り替え）。CMS 側のトークン発行とプレビュー API の提供までが本仕様の範囲（design.md 5.7.2）
- 複数ユーザーの権限分離（ロール管理）。許可ユーザーは全員同一権限とする
- PV・いいね等の動的な集計データ
- 全文検索エンジンの導入（インデックス内の部分一致検索までを提供）
- 多言語対応（i18n）
- WYSIWYG エディタ（Markdown エディタ + プレビューとする）

## 4. 確定済みの技術選定と制約

ユーザー確認済みの決定事項。設計・実装フェーズではこれを前提とする。

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| コンテンツ保存先 | **別リポジトリ**（private、例: `nextjs-cms-content`） | コンテンツ更新でアプリの再デプロイが走らない。権限をコンテンツ用に分離できる |
| 書き込み方式 | **作業ブランチ + Pull Request** | 下書き状態を持たせたい。公開前に GitHub 上で差分レビューできる |
| 認証 | **GitHub OAuth のみ・DB なし** | 認証用の DB を持たない。許可ユーザー/Org を allowlist で制限 |
| 書き込み権限 | **GitHub App のインストールトークン** | 長期シークレットをクライアントに置かない。content リポジトリのみにスコープを限定 |
| 画像 | **ImageKit**（Upload API **V2** / JWT 方式） | 無料枠内でリサイズ・WebP 変換・最適化を URL パラメータで完結できる。V2 の JWT はアップロードペイロード全体を署名が束縛するため、クライアントがフォルダ・ファイル名を改変できない |
| 全体構成 | **3リポジトリ**（`nextjs-cms` / `nextjs-cms-content` / 公開サイト） | データとコードを分離し、記事更新でアプリが再デプロイされないようにする |
| アプリ構成 | Next.js 単一アプリ（Admin UI + 公開 API + 管理 API） | Admin と管理 API が同一プロセスにあるためサービス間認証が不要になり、攻撃対象面が最小になる。将来 API を別デプロイへ切り出せる構造にする |
| 公開サイト | 別リポジトリ・別デプロイ。公開 API 経由でのみコンテンツを取得する | 公開サイト側に GitHub の資格情報が一切不要になる |
| コンテンツの正 | **Markdown のみ**。HTML は保存しない | HTML を保存すると Git の差分が読めなくなり、PR レビューという本設計の中心的な利点を失う |
| Markdown → HTML 変換 | **アプリ側のランタイムで実行**し、結果をキャッシュする | 公開 API・エディタプレビュー・下書きプレビューが同一実装を共有でき、プレビューと本番の出力が原理的に一致する |
| インデックス生成 | **アプリ側で Webhook 契機に再構築**（content リポジトリに GitHub Actions を置かない） | frontmatter スキーマ・変換処理をアプリ側の単一実装に保てる。生成コミットによる push ループも構造的に発生しない |
| 技術スタック | Next.js (App Router) / TypeScript / Hono / Zod / Biome / Vitest | README 記載の既存選定を踏襲 |
| UI コンポーネント | **`@zukki30/zukki-design-system`**（自前のデザインシステム） | 既存資産を活用し、見た目と a11y の基準を他プロジェクトと揃える |
| スタイリング | **CSS Modules + デザインシステムの CSS 変数**。Tailwind は使わない | トークンの尺度が二重化するのを避ける |
| パッケージ管理 | **pnpm**（バージョンは mise で固定） | デザインシステム側と揃える |

### 4.1 前提とする外部サービスの制約

- GitHub REST API のレート制限は認証済みで **5,000 req/hour** が基準（GitHub App のインストールトークンは対象リポジトリ数に応じて上限が上がる）。公開 API がリクエストごとに GitHub を叩く設計は成立しない。
- content リポジトリは **private 必須**。public にすると `raw.githubusercontent.com` 経由で無料・高速に読める利点があるが、下書きブランチの内容も公開されてしまうため採用しない。
- ImageKit の無料枠は **月 20 GB の転送量・3 GB のストレージ・2 ユーザー**（2026-10 時点）。転送量より **ストレージ 3 GB が先に上限に達する**ため、アップロード時の原本サイズを制限する。変換後の派生画像はストレージを消費せず転送量側にのみ計上される。
- ImageKit のクライアント直アップロードには V1（token + expire + signature）と V2（単一 JWT）があり、**V1 は署名が `token` と `expire` しか束縛せず、`folder` や `fileName` の改変を防げない**。本仕様では V2 のみを使用する。V2 には公式 SDK がないため直接 HTTP で実装する。

## 5. 機能要件

### 5.1 認証・認可

| ID | 要件 |
| --- | --- |
| FR-AUTH-01 | 未認証のユーザーが `/admin` 配下および `/api/admin` 配下にアクセスした場合、Admin のログイン画面へリダイレクト（API は 401 を返す） |
| FR-AUTH-02 | ログインは GitHub OAuth のみ。メール+パスワードや他のソーシャルログインは提供しない |
| FR-AUTH-03 | OAuth 認証後、GitHub のユーザー名が許可リスト（env で指定）に含まれるか、指定 Organization のメンバーである場合のみログインを許可する。それ以外は明示的に拒否する |
| FR-AUTH-04 | 取得したユーザーの GitHub アクセストークンは本人確認に使用した後に破棄し、サーバー・クライアントのいずれにも永続化しない |
| FR-AUTH-05 | セッションは HttpOnly / Secure / SameSite=Lax の暗号化 Cookie で保持する。有効期限を持ち、期限切れ後は再ログインを要求する |
| FR-AUTH-06 | ログアウト操作でセッション Cookie を無効化できる |
| FR-AUTH-07 | content リポジトリへの書き込みは、サーバー側でその都度発行する GitHub App のインストールトークンで行う。コミットの author にはログインユーザーの表示名とメールアドレスを設定する |

### 5.2 コンテンツ共通（News / Blog / FAQ）

| ID | 要件 |
| --- | --- |
| FR-CONTENT-01 | 各コンテンツタイプのエントリ一覧を Admin で閲覧できる。公開済み・下書き・公開予約・非公開を状態として区別して表示する |
| FR-CONTENT-02 | 一覧はタイトル・状態での絞り込みと、更新日時・公開日時での並び替えができる |
| FR-CONTENT-03 | エントリを新規作成できる。作成時に ID（ULID、以後不変）が自動付与される |
| FR-CONTENT-04 | エントリを編集できる。本文は Markdown で入力し、プレビューを確認できる |
| FR-CONTENT-05 | エントリを削除できる。削除はファイル削除のコミットとして記録され、Git 履歴から復元可能である |
| FR-CONTENT-06 | 公開中のエントリを「非公開」にできる。ファイルは削除せず状態のみ変更する |
| FR-CONTENT-07 | slug はコンテンツタイプ内で一意である。重複する slug での保存はエラーとして拒否する |
| FR-CONTENT-08 | slug を変更しても ID は変わらない。公開 API は ID でも slug でも詳細を取得できる |
| FR-CONTENT-09 | 公開日時を未来の日時で指定できる（公開予約）。公開 API は指定日時を過ぎるまでそのエントリを返さない |
| FR-CONTENT-10 | 保存時に必須項目の検証を行い、不足・不正な値はフィールド単位のエラーとして Admin に表示する |

### 5.3 下書きと公開（Pull Request フロー）

| ID | 要件 |
| --- | --- |
| FR-DRAFT-01 | エントリを「下書き保存」すると、content リポジトリに専用の作業ブランチが作られ、変更がコミットされる。main には影響しない |
| FR-DRAFT-02 | 同じエントリに対する2回目以降の下書き保存は、同じ作業ブランチへの追加コミットとなる |
| FR-DRAFT-03 | 下書きに対応する Pull Request が自動で作成される。PR のタイトル・本文からコンテンツタイプとタイトルが判別できる |
| FR-DRAFT-04 | Admin は未マージの Pull Request 一覧を「下書き」として表示する。各下書きから GitHub の PR ページへ遷移できる |
| FR-DRAFT-05 | Admin から下書きの**本文プレビュー**を確認できる。作業ブランチの内容を読み取り、認証済みユーザーのみ閲覧できる。公開サイトの CSS・レイアウトは反映されず、Markdown の変換結果のみを表示する |
| FR-DRAFT-06 | Admin から「公開」操作を行うと Pull Request がマージされ、作業ブランチが削除される |
| FR-DRAFT-07 | 作業ブランチが main と競合してマージ不能な場合、公開操作を実行せず競合していることを Admin に表示する |
| FR-DRAFT-08 | 下書きを破棄できる。Pull Request をクローズし作業ブランチを削除する |
| FR-DRAFT-09 | 既に公開済みのエントリを編集した場合も同じフローに乗る（作業ブランチで編集 → PR → マージで反映） |

#### 実表示プレビュー（公開サイト連携）

公開サイトのレイアウトで下書きを確認するための仕組み。**公開サイトの構築時に実施する**（CMS 側のエンドポイント提供までが本仕様の範囲）。

| ID | 要件 |
| --- | --- |
| FR-PREVIEW-01 | Admin から、公開サイトのレイアウトで下書きを表示するプレビューを開ける |
| FR-PREVIEW-02 | プレビューの開始には、CMS が発行する**短命の署名付きトークン**を用いる。トークンには対象のコンテンツタイプと ID を含め、有効期限は数分程度とする |
| FR-PREVIEW-03 | CMS はトークンを検証し、トークンが示すリソースと要求されたリソースが一致する場合のみ下書きの内容を返す。一致しない場合は拒否する |
| FR-PREVIEW-04 | トークンの検証は CMS 側だけで行い、**公開サイトに共有シークレットを持たせない** |
| FR-PREVIEW-05 | プレビュー用のエンドポイントは公開 API とは分離し、検索エンジンにインデックスされないようにする |
| FR-PREVIEW-06 | 下書きが公開 API（`/api/v1/*`）から取得できないという原則は、プレビュー機能の追加後も維持される |

### 5.4 カテゴリー・タグ

| ID | 要件 |
| --- | --- |
| FR-TAXO-01 | News と Blog に対して、それぞれ独立したカテゴリーとタグを作成・編集・削除できる |
| FR-TAXO-02 | カテゴリー・タグは名称・slug・説明・表示順を持つ |
| FR-TAXO-03 | エントリの編集画面から新しいカテゴリー・タグを作成し、そのまま選択できる |
| FR-TAXO-04 | エントリ編集中に作成したタクソノミーは、そのエントリの作業ブランチにコミットされる。選択候補には main 上のタクソノミーと作業ブランチ上のタクソノミーの両方が表示される |
| FR-TAXO-05 | エントリに紐付いているカテゴリー・タグを削除しようとした場合、使用中であることを警告する |
| FR-TAXO-06 | カテゴリーは1エントリに複数設定でき、タグも複数設定できる |
| FR-TAXO-07 | FAQ はカテゴリー・タグを持たない。代わりに表示順を指定できる |

### 5.5 画像

| ID | 要件 |
| --- | --- |
| FR-IMG-01 | Admin から画像をアップロードできる。アップロードは ImageKit へ直接行い、アプリサーバーを画像データが経由しない |
| FR-IMG-02 | アップロードは**サーバーが発行した JWT を伴うリクエストのみ**受け付ける。JWT はアップロード先フォルダ・ファイル名を含むペイロード全体を束縛し、クライアントによる改変を無効化する |
| FR-IMG-03 | アップロード可能な形式（JPEG / PNG / WebP / GIF。SVG は除く）と最大ファイルサイズ（5 MB）をサーバー側で制限する |
| FR-IMG-04 | アップロード済み画像を一覧・検索でき、エントリのアイキャッチ画像や本文への挿入に再利用できる |
| FR-IMG-05 | 画像を削除できる。削除時にその画像を参照しているエントリがあれば警告する |
| FR-IMG-06 | 画像は識別子（`fileId`）・URL・代替テキスト・幅・高さを伴って Markdown の frontmatter または本文に記録される |
| FR-IMG-07 | コンテンツタイプごとにフォルダを分けて保管する（例: `news/`, `blog/`, `faq/`） |
| FR-IMG-08 | 本 CMS を複製して複数プロジェクトで運用する場合に備え、保管フォルダの先頭にプロジェクト識別子を付けられるようにする。未設定時は従来どおりコンテンツタイプ直下に保管する |

### 5.6 公開 API

| ID | 要件 |
| --- | --- |
| FR-API-01 | 認証不要の読み取り専用 API として提供する。書き込み系の操作は一切公開しない |
| FR-API-02 | コンテンツタイプごとの一覧を取得できる。カテゴリー・タグ・キーワードでの絞り込み、並び替え、ページネーションに対応する |
| FR-API-03 | slug または ID による詳細取得ができる |
| FR-API-04 | 一覧・詳細ともに、公開済みかつ公開日時を過ぎたエントリのみを返す。下書き・非公開・公開予約中のエントリは返さない |
| FR-API-05 | カテゴリー一覧・タグ一覧を、それぞれの公開済みエントリ件数とともに取得できる |
| FR-API-06 | 詳細取得時に本文の形式を `format` クエリパラメータで選択できる。`html`（既定） / `markdown` / `both` の3種とする |
| FR-API-07 | 一覧レスポンスには本文を含めない（メタデータと `excerpt` のみ）。本文は詳細取得で返す |
| FR-API-08 | 存在しないリソースは 404、不正なクエリパラメータは 400 を、いずれも機械可読なエラー形式で返す |
| FR-API-09 | レスポンスは CORS により外部サイトからの取得を許可する |

### 5.7 Markdown の変換

| ID | 要件 |
| --- | --- |
| FR-MD-01 | Markdown から HTML への変換処理はアプリ内の単一モジュールとして実装し、公開 API・エディタプレビュー・下書きプレビューがすべて同じ実装を使用する |
| FR-MD-02 | 変換結果の HTML はサニタイズ済みであること（Markdown 内の生 HTML による XSS を防ぐ） |
| FR-MD-03 | 変換時にコードブロックのシンタックスハイライトを適用する。クライアント側でハイライト用のスクリプトを読み込む必要がないこと |
| FR-MD-04 | 変換時に見出しへ `id` を付与し、目次（見出しの階層構造）をレスポンスに含められること |
| FR-MD-05 | 本文中の画像に対し、レイアウトシフトを防ぐための `width` / `height` と遅延読み込みの指定を変換時に補完する |
| FR-MD-06 | 変換結果はキャッシュし、同一エントリに対する2回目以降のリクエストで再変換しないこと |

### 5.8 キャッシュとインデックス

| ID | 要件 |
| --- | --- |
| FR-CACHE-01 | 公開 API は、リクエストごとに GitHub API を呼び出さない。インデックスとエントリの変換結果をキャッシュして応答する |
| FR-CACHE-02 | インデックスはアプリ側で構築する。content リポジトリには GitHub Actions のワークフローも生成ファイルも配置しない |
| FR-CACHE-03 | content リポジトリの main が更新されたとき、Webhook を契機にインデックスが再構築され、関連するキャッシュが破棄される |
| FR-CACHE-04 | インデックスの構築は、全エントリの frontmatter を一括取得する方式とし、エントリ数に比例した大量の API 呼び出しを発生させないこと |
| FR-CACHE-05 | Webhook は署名検証を行い、検証に失敗したリクエストは処理しない |
| FR-CACHE-06 | Webhook が失敗・不達だった場合でも、一定時間が経過すればキャッシュが期限切れとなり最新内容が反映される（Webhook に単独依存しない） |
| FR-CACHE-07 | 公開予約されたエントリは、追加の手動操作なしに公開日時を過ぎた時点で公開 API から取得できるようになる |
| FR-CACHE-08 | content リポジトリを GitHub 上で直接編集した場合も、Admin を経由した更新と同じ経路で反映される |

## 6. データモデル要件

### 6.1 content リポジトリのディレクトリ構成

```
content/
├── news/<slug>.md
├── blog/<slug>.md
├── faq/<slug>.md
└── _taxonomies/
    ├── news/categories/<slug>.md
    ├── news/tags/<slug>.md
    ├── blog/categories/<slug>.md
    └── blog/tags/<slug>.md
```

content リポジトリは `content/` 配下のコンテンツのみを保持する。ワークフロー定義・生成ファイル・アプリケーションコードは一切置かない。

| ID | 要件 |
| --- | --- |
| FR-DATA-01 | 1エントリ = 1ファイル。YAML frontmatter（メタデータ）+ Markdown 本文の形式とする |
| FR-DATA-02 | カテゴリー・タグも 1語 = 1ファイルとする。単一の YAML に集約すると、PR フローで必ず同じ行が競合するため採用しない |
| FR-DATA-03 | frontmatter は Zod スキーマで検証する。スキーマはアプリ内の単一の場所で定義し、Admin のフォーム検証・インデックス構築・公開 API のすべてがそれを共有する |
| FR-DATA-04 | エントリ共通の必須項目: `id` / `slug` / `title` / `status` / `createdAt` / `updatedAt` |
| FR-DATA-05 | News / Blog の項目: `publishedAt` / `categories` / `tags` / `excerpt` / `coverImage` |
| FR-DATA-06 | FAQ の項目: `publishedAt` / `order` |
| FR-DATA-07 | `status` は `published` / `archived` の2値。下書きはブランチの存在で表現するため `draft` 値は持たない |
| FR-DATA-08 | 日時は ISO 8601（タイムゾーン付き）で記録する |

## 8. 受け入れ基準

1. 許可されていない GitHub ユーザーで Admin にログインできないこと
2. News / Blog / FAQ それぞれで、作成 → 下書き保存 → プレビュー確認 → 公開 → 公開 API で取得、までが一連で完了すること
3. 下書き状態のエントリが、公開 API のどのエンドポイントからも取得できないこと
4. News / Blog でカテゴリーとタグを新規作成し、エントリに紐付けて、公開 API の絞り込みで利用できること
5. 画像をアップロードしてアイキャッチに設定し、公開 API のレスポンスに URL が含まれること
6. 公開日時を未来に設定したエントリが、その日時を過ぎるまで公開 API から取得できないこと
7. content リポジトリを GitHub 上で直接編集（main への push）した場合も、公開 API に反映されること
8. 同一エントリを2つのセッションから編集した場合、後から保存した側が競合として拒否され、変更が失われないこと
9. 詳細取得で `format=html` / `markdown` / `both` がいずれも期待どおりのレスポンスを返し、Admin のプレビューと `format=html` の出力が一致すること
10. Markdown に生 HTML（`<script>` 等）を記述しても、HTML 出力から除去されていること
11. lint / 型チェック / テストがすべて通ること
